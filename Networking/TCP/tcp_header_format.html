TCP Header Format

A clear guide to the fields, control bits, checksum, options, and user data in a TCP segment.

1. Overview

TCP segments are carried inside IP packets. The IP header contains the source and destination host addresses. The TCP header follows the IP header.

This separation allows other transport protocols to use IP. TCP adds the information that is required to provide TCP communication.

Key point: This page describes the TCP header used by TCP. The IP header is not part of the TCP header.

See RFC 9293 — Header Format

2. TCP header

The TCP header is followed by the user data carried by the segment. The header contains fields for ports, sequence control, acknowledgments, flow control, error detection, urgent data, and options.

16 bits Destination Port
16 bits
Sequence Number — 32 bits
Acknowledgment Number — 32 bits
Data
Offset Reserved Control bits Window — 16 bits
Checksum — 16 bits Urgent Pointer — 16 bits
Options and padding — variable

3. Header fields

Source Port
16 bits
The port number of the sender.
Destination Port
16 bits
The port number of the receiver.
Sequence Number
32 bits
The sequence number of the first data octet in this segment. If SYN is set, the value is the Initial Sequence Number (ISN). The first data octet then has sequence number ISN + 1.
Acknowledgment Number
32 bits
If ACK is set, this field contains the next sequence number that the sender expects to receive. After a connection is established, TCP sends this field.
Data Offset (DOffset)
4 bits
The number of 32-bit words in the TCP header. It shows where the user data starts. The complete TCP header is always a whole number of 32-bit words.
Reserved
4 bits
Bits reserved for future use. A sender must set these bits to zero. A receiver must ignore them when the related future feature is not implemented.
Window
16 bits
The number of data octets, starting at the acknowledged sequence number, that the sender is ready to receive. Window scaling can change the effective window size.
Requirement: Treat the window value as an unsigned number. Otherwise, large window values can appear negative and TCP can fail.
Recommendation: Implementations should reserve 32-bit fields for send and receive window sizes and perform window calculations with 32 bits.
Checksum
16 bits
The checksum detects errors in the TCP header and data. It also includes an IP pseudo-header in the checksum calculation.
Urgent Pointer
16 bits
The current urgent-pointer value is a positive offset from the sequence number in the segment. It points to the sequence number of the octet after the urgent data. Interpret this field only when URG is set.
Options
Variable
TCP options can extend the header. Options are present when DOffset > 5. Padding can be included after the actual options.

4. Control bits

Control bits are also called flags. IANA manages the assignment of TCP header flags. The currently assigned flags are:

CWRCongestion Window Reduced.
ECEECN-Echo.
URGUrgent pointer is significant.
ACKAcknowledgment field is significant.
PSHPush function.
RSTReset the connection.
SYNSynchronize sequence numbers.
FINNo more data from the sender.

See IANA TCP Header Flags Registry

5. Checksum

The TCP checksum is a 16-bit one's-complement checksum. It covers the TCP header and TCP data.

Checksum alignment

The checksum calculation works with 16-bit words. If the header and data contain an odd number of octets, add a zero octet on the right for the calculation. This padding is not sent as part of the TCP segment.

Before the calculation, set the checksum field itself to zero.

IP pseudo-header

The checksum also covers a pseudo-header. The pseudo-header helps protect a TCP connection against incorrectly routed segments.

IPv496-bit pseudo-header.
IPv6320-bit pseudo-header.

IPv4 pseudo-header fields

Field Meaning
Source Address IPv4 source address, in network byte order.
Destination Address IPv4 destination address, in network byte order.
Zero Bits set to zero.
PTCL Protocol number from the IP header.
TCP Length TCP header length plus TCP data length, in octets. It does not include the 12-octet IPv4 pseudo-header.

IPv6 pseudo-header

RFC 8200 defines the IPv6 pseudo-header. It contains the IPv6 source and destination addresses, the upper-layer packet length, three zero-padding bytes, and a Next Header value. The Next Header value can differ from the IPv6 header value when IPv6 extension headers are present.

Mandatory: The TCP checksum is never optional. The sender must generate it. The receiver must check it.

6. TCP options

TCP options can appear at the end of the TCP header. Their total space is:

Options size = (DOffset − 5) × 32 bits

This size includes any padding after the actual options.

Option format

Options are multiples of 8 bits. An option can start at any octet boundary.

Case Format
Case 1 One octet containing the option kind.
Case 2 Option kind + option length + option data.

The option length includes the option-kind octet, the option-length octet, and all option-data octets.

Padding rule: The option list can be shorter than the space indicated by DOffset. After the End of Option List option, the remaining header space must contain zero padding.

IANA maintains the list of defined TCP options. Each option is specified by another RFC. The list also includes experimental options.

7. Mandatory options

A TCP implementation can support any defined TCP option. It must support the following options:

Kind Length Meaning
0 — End of Option List (EOL)
1 — No-Operation (NOP)
2 4 Maximum Segment Size (MSS)
Receive rule: A TCP implementation must be able to receive a TCP option in any segment.
Unknown options: If an option has a length field and the implementation does not support it, the implementation must ignore it without error.
Length rule: All TCP options except EOL and NOP must have a length field. Future options must also have a length field.
Invalid length: Implementations must handle illegal option lengths, such as zero. One suggested action is to reset the connection and record the error.

Work is also in progress to extend the space available for TCP options.

See RFC 9293 — Option Definitions

8. User data

Data
Variable length
User data carried by the TCP segment.

The TCP header is followed by this data. The data length is not fixed by the TCP header format.

Quick reference

Area Main rule
Ports Identify the TCP source and destination ports.
Sequence / ACK Control the position of data and confirm received data.
DOffset Shows where TCP data begins.
Flags Control TCP functions such as SYN, ACK, RST, and FIN.
Window Shows how much data the receiver is ready to accept.
Checksum Must be generated by the sender and checked by the receiver.
Options Extend the TCP header and must follow TCP option rules.
Data Carries user data and has variable length.
